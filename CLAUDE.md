# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visión general

Ruteando es una aplicación web de planificación de rutas. La migración desde AngularJS terminó: el repositorio contiene un único frontend y un servidor mínimo. El código de la aplicación AngularJS anterior (`master/`, `externModules/`, `json/`, el backend de ejemplo de Satellizer) solo existe en el historial de git; el último commit que lo contiene es `19b1cb4`.

| Directorio | Qué es |
|---|---|
| `ng-ruteando/` | Frontend Angular 21.2 (standalone, scss, SSR con `server.ts`, zone.js conservado) con Angular Material 21.2 (tema M3): acceso, flota, lugares, paquetes, configuraciones, jornadas (con mapa de rutas, detalle de ruta y visitas) y zonas, sobre el HanoIT Gateway. Ver los changes de `openspec/`. |
| `server/` | Servidor Express mínimo: reenvía `/gateway/**` al HanoIT Gateway (`gateway-proxy.js`), publica la compilación de navegador de `ng-ruteando` y responde la página de la aplicación a las rutas del cliente. Pruebas en `server/test/`. |
| `openspec/` | Specs vigentes (`specs/`) y changes (`changes/`, con `archive/` para los terminados). |
| `scripts/` | `extract-gateway-fixtures.mjs`: regenera los fixtures sanitizados del gateway. |

## Comandos

### Frontend Angular (`ng-ruteando/`)
Requiere Node `^20.19 || ^22.12 || >=24` (`ng-ruteando/.nvmrc` = 22; usa `nvm use`). `npm ci`, `npm start` (dev, puerto 4200), `npm run build`, `npm test` (Karma interactivo), `npm run test:ci` (una ejecución con Chrome sin interfaz) y `npm run serve:ssr:ng-ruteando` tras compilar (puerto 4000).

Entornos: `src/environments/environment.ts` (producción) y `environment.development.ts` (`ng serve`) definen `apiUrl` (`/gateway`), que se provee con el token `API_BASE_URL`. `ng serve` usa `ng-ruteando/proxy.conf.js`, que reenvía `/gateway` al gateway con `X-Api-Key` tomada de `GATEWAY_URL` y `GATEWAY_API_KEY` (entorno o `.env` de la raíz); sin ellas avisa y responde 503. Ver «Proxy del HanoIT Gateway» más abajo.

### Integración continua
`.github/workflows/ci.yml` (trabajos `frontend`, `server`, `specs`, `audit` y el resumen `ci`, que es la comprobación obligatoria de `main`) y `.github/dependabot.yml`. Las acciones van fijadas por SHA con su versión en un comentario (se resuelven con `gh api repos/<acción>/git/ref/tags/<versión>`), el CLI de OpenSpec está fijado en `OPENSPEC_VERSION` y se instala `npm@11` porque el de Node 22 puede fallar al instalar desde cero. La auditoría de producción (`npm audit --omit=dev --audit-level=high`) debe estar limpia en la raíz y en `ng-ruteando/`; `jspdf` y `@faker-js/faker` se retiraron por no usarse. Los comandos para repetirlo en local están en `README.md`.

### Servidor (`server/` y raíz)
- `npm ci` y `npm start` en la raíz ejecutan `node server/server.js`; las dependencias del servidor (`express`, `morgan`, `colors`, `http-proxy-middleware`) están en el `package.json` de la raíz. No hay base de datos ni MongoDB.
- Puerto: `PORT` o 3000. `server.js` carga `.env`, registra el proxy `/gateway`, responde 404 en JSON a `/api/*` y `/auth/*` (no son rutas del cliente), publica `ng-ruteando/dist/ng-ruteando/browser` (se cambia con `WEB_DIST`) y responde `index.csr.html` a las rutas del cliente; los ficheros inexistentes devuelven 404. Hay que compilar antes con `npm run build:web` (sin compilación el servidor arranca, avisa en el log y responde 503 en las rutas del cliente). El estático y el comodín van siempre al final de `server.js`.
- `npm run test:server` ejecuta las pruebas del servidor (`server/test/*.test.js`, `node:test`).
- La app Angular consume el **HanoIT Gateway** a través del proxy `/gateway` (ver abajo).

### Proxy del HanoIT Gateway (`/gateway`)
El servidor reenvía `/gateway/**` a `<GATEWAY_URL>/api/v1/**` y añade la cabecera `X-Api-Key` desde el servidor (`server/gateway-proxy.js`); el navegador nunca ve la clave y no hay CORS. Se configura con variables de entorno: copia `.env.example` a `.env` (ignorado por git) y rellena `GATEWAY_URL` y `GATEWAY_API_KEY`; `GATEWAY_TIMEOUT_MS` (opcional, 30000 por defecto). `server.js` carga `.env` al arrancar y no pisa variables ya definidas en el entorno. Sin esas variables el servidor arranca, avisa en el log y responde 503 en `/gateway/**`; si el gateway cae responde 502 y si tarda demasiado 504. La clave es un secreto: no la copies a ficheros versionados, a `environment*.ts` ni al frontend. El proxy se registra antes de `body-parser` para reenviar el cuerpo en streaming (multipart), y las rutas `/api/*` y `/auth/*` del propio servidor no pasan por él.

### Cabeceras de seguridad
`server/security-headers.js` añade a todas las respuestas (antes del proxy y del estático) `nosniff`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`, `COOP`, HSTS solo con `X-Forwarded-Proto: https` y una CSP (`script-src 'self'`; solo Google Fonts y las teselas de OpenStreetMap como orígenes externos). `CSP_MODE` (`report-only` por defecto, `enforce`, `off`) y `CSP_IMG_SRC` (otro proveedor de teselas) la configuran. La compilación de producción desactiva `optimization.styles.inlineCritical` (`angular.json`): la carga diferida de los estilos críticos añade un `onload` que la CSP bloquea y rompe los estilos; no lo reactives. Verificado en navegador con `enforce`: sin violaciones. Tras añadir recursos externos o scripts en línea, comprueba con `report-only` antes de usar `enforce`.

## Arquitectura / puntos a tener en cuenta

- Autenticación: la sesión es del gateway (`/auth/*` por `/gateway`); el servidor propio no autentica. `AuthService` restaura la sesión al arrancar y la renueva antes de que caduque, el interceptor de renovación reintenta en 401 con una sola petición compartida, y `TokenStorageService` guarda el access token en memoria y el refresh token en `localStorage` (`hanoitToken`, `hanoitTokenExpiresDate`, las mismas claves que usaba la app AngularJS); la caducidad se calcula con `Date.now() + expires_in * 1000` y el servicio es seguro en SSR.
- Consumo del gateway (`ng-ruteando/src/app/core/`): `api/` (interceptores, errores en español personalizables, paginación, servicios `data/*.api.ts`, modelos), `auth/` (sesión, guards, `TokenStorageService` seguro en SSR) y `geo/` (`LatLng`, polilíneas de precisión 5). Las coordenadas del gateway son `[lon, lat]`; en el dominio se usa `LatLng`. El campo `geoJson` de las rutas es una polilínea codificada, no GeoJSON. La subida de CSV y la geocodificación no tienen contrato documentado todavía. Pantallas de acceso en `ng-ruteando/src/app/features/access/` (`/acceso`, `/acceso/registro`, `/acceso/recuperar`, `/acceso/verificar-email?token=`, `/acceso/restablecer?token=`): layout propio sin shell; el área privada (`''`, con el shell diferido) exige sesión y `/` ya no es pública; el destino tras el login pasa siempre por `safeReturnUrl`. `POST /auth/logout` lleva `{ refreshToken }`. Flota en `ng-ruteando/src/app/features/fleet/` (`/flota/tipos`, `/flota/vehiculos`, `/flota/conductores`, solo `tenant_admin` y `super_admin`) sobre el patrón de listado, borrado y envío de `shared/data/`. Lugares en `features/places/` (`/lugares`) y mapa reutilizable en `shared/map/` (OpenLayers cargado solo en el navegador; teselas de OpenStreetMap configuradas en `environment*.ts`). Paquetes en `features/packages/` (`/paquetes`; administradores y agentes; exportación e importación de CSV con `shared/data/csv.ts`; la importación (`/paquetes/importar`) lee el archivo en el navegador y crea los paquetes uno a uno porque `POST /packages/upload` no tiene contrato, y exige coordenadas porque no hay geocodificación). Configuraciones de planificación en `features/settings/` (`/configuraciones`, solo administradores; secciones según el tipo de restricción) y `shift-time` compartido en `shared/time/`. Jornadas en `features/journeys/` (`/jornadas`: planificar con configuración y paquetes elegidos, listar y detalle con rutas y paradas; administradores y agentes). El detalle de la jornada pinta sus rutas en un mapa (`RoutesMapComponent`: color por ruta, paradas numeradas, leyenda y ficha accesibles). Cada ruta tiene su detalle en `/jornadas/:id/rutas/:routeIndex` con mapa de esa ruta y seguimiento de visitas: una visita es una parada con `packageId`, su estado es el del paquete (`PATCH /packages/{id}/status/{status}`) y se lee con una petición por paquete (de a 6) porque no hay recurso de visitas ni endpoint por lotes. Zonas en `features/zones/` (`/zonas`, solo administradores) con el editor de polígonos de `shared/map/` (`PolygonEditorComponent` + `VertexTableComponent` sobre `polygon-geometry.ts`; la lista de vértices es la fuente de verdad y la tabla es la alternativa accesible). Auditoría en `features/audit/` (`/auditoria`, una sola pantalla; `tenant_admin`, `super_admin` y `agent`): lee los cuatro `GET /audit-logs*` con `AuditLogsApi`, que entrega la página `number` del gateway como `Page<T>`. Ámbitos por rol (`audit-scopes.ts`): «Mi empresa» (`tenant_admin`), «Todas las empresas» (`super_admin`, con empresa opcional por `tenantId`) y «Mi actividad» (todos; el agente solo tiene este, sin filtro ni cifra de persona). Los eventos del ámbito se cargan enteros en el cliente (`AuditStore` sobre `FullListState`, tope 1000) y **la dirección de la página es la única fuente de los filtros** (`audit-filters.ts`: `ambito`, `empresa`, `q`, `entidad`, `accion`, `persona`, `rango` o `desde`/`hasta`, `cambios`, `id`; lo inválido se ignora): la búsqueda y el chip de entidad son los de `DataTableComponent` (por eso `filter` y `facetKey` son `model()`, enlazables con `[(filter)]` y `[(facetKey)]`) y los demás filtros pasan antes por `AuditViewState`. La tabla y las tarjetas llevan solo lo esencial (acción, quién, cuándo) y un ojo siempre visible por fila. La lógica es pura y se prueba sin `TestBed` (`audit-labels`: acciones, tipos, roles y frases; `-diff`, `-filters`, `-stats`, `-links`, `-export`). El detalle completo es una modal (`AuditDetailDialogComponent`, cargada con `import()` al abrir el primer evento) que sigue a `?evento=<id>` en la dirección: el ojo o la tarjeta ponen el parámetro, el listado abre la modal al terminar de cargar con el evento que ya tiene (si no está entre los traídos la modal lo pide con `GET /audit-logs/{id}`; los agentes reciben 403 ahí y se les explica), cerrar quita el parámetro (con `Location.back()` si se empujó al abrir) y `closeOnNavigation` va en `false` porque Material cerraba la modal antes que el router y el cierre pedía otro «atrás». La modal se compone de `AuditDetailHead` (tono y glifo por tipo de acción), `AuditFacts` (avatar con `actorInitials`), `AuditChanges` (antes → después), `AuditRelated` (línea de tiempo de la misma entidad desde lo ya traído; saltar a otro evento reemplaza la dirección) y `AuditTech`. «Mostrar datos técnicos» (`ruteando-audit-tech`) añade la columna «Clave» a la tabla y abre el bloque `AuditTech` de la modal; la frase de la modal abrevia los identificadores largos (`humanizeIds`). **Los estilos van en la hoja de cada componente (`ViewEncapsulation.None`), no en `styles.scss`**: un parcial global subió el bundle inicial por encima de los 500 kB, y cada hoja debe quedar bajo 2 kB (de ahí el reparto en `ActivityBars`, `ActivityShares`, `AuditEventCard` y los cinco componentes de la modal). Todo texto del gateway se pinta como texto (hay pruebas con HTML en descripciones y valores). Sin verificar contra el gateway real: `openspec/changes/add-audit-module/tasks.md` 10.2. `POST /journeys/plan` falla en el gateway real con ids hexadecimales (defecto del backend) y `GATEWAY_TIMEOUT_MS` puede necesitar subirse. Detalle y mapeo (histórico) legacy -> gateway en `.claude/skills/angular-ruteando/references/gateway-api.md`; fixtures reales saneados en `ng-ruteando/src/testing/fixtures/gateway/` (se regeneran con `node scripts/extract-gateway-fixtures.mjs <colección>`).
- Sistema de interfaz (toda la aplicación): un único tema Material 3 claro y oscuro automático (`color-scheme: light dark`, `theme-type: color-scheme`) definido en `ng-ruteando/src/styles.scss`. El estilo común vive en `src/app/shared/ui/_ui-system.scss` (clases `.page`, `.page-head`, `.card`, `.stat-grid`, `.tile`, `form.card`, `.form-grid`, `.form-actions`, `.visually-hidden`, con selectores `:where` de baja especificidad) y las etiquetas de estado en `shared/ui/status-badge.component.ts` con `statusTone(dominio, clave)`. Los estados usan colores con su significado (verde, azul y ámbar: `--app-{success,info,warning}-container` y sus `--app-on-…`, definidos una sola vez en `styles.scss` con `light-dark()`; el peligro usa `error-container` y el neutro, `surface-container-highest`); no uses los colores de la marca para un estado. El hilo de la marca es `--app-brand-gradient` (primario a terciario), solo para el botón principal de los formularios de acceso, la acción principal de Inicio, barras de progreso y una palabra destacada: sobre un `mat-flat-button` el selector debe ganar a `.mdc-button { background: transparent }` (no uses `:where()`). **Tema**: sigue al sistema salvo que la persona elija Claro u Oscuro con `ThemeToggleComponent` (barra del shell y arriba a la derecha de las pantallas de acceso); `ThemeService` guarda la elección en `localStorage` (`ruteando-theme`) y la aplica con `data-theme` en `<html>` (`html[data-theme]` en `styles.scss` solo cambia `color-scheme`, el tema no se redefine), y `src/assets/theme-init.js` la aplica antes del primer pintado: es un fichero y no un script en línea porque la CSP solo admite `script-src 'self'` (misma clave y valores que el servicio). Regla: los componentes **no repiten** estilos de título, resumen, superficie ni `:host { display: block }` en pantallas enrutadas (anularía el ritmo vertical del marco `.page`); el icono de la etiqueta usa `fontIcon` para que el texto de la celda sea solo el nombre del estado. Las teselas del mapa se oscurecen en tema oscuro (ver «Resto de pantallas»).
- Vista de acceso (`ng-ruteando/src/app/features/access/`): el aspecto común de título, formulario, botón principal y enlaces es **solo de esta vista**, acotado a la clase `.access-theme` del layout (`_access-theme.scss`, cargado desde `styles.scss`); el tema (claro y oscuro) es el global. La marca (`shared/brand/brand.component.ts`, también en la barra del shell con `size="compact"`) y la ilustración de rutas (`shared/brand/route-backdrop.component.ts`, que también usa la cabecera de Inicio) son SVG inline sin imágenes, con colores del tema (las rutas usan `routeColorThemed`: `light-dark()` entre `ROUTE_COLORS` y la variante luminosa `ROUTE_COLORS_DARK`; el mapa de OpenLayers sigue con `routeColor`, que no entiende `light-dark()`), y las pantallas no declaran estilos propios de título, formulario ni enlaces. Layout (`access-layout.component.*`): tarjeta centrada sobre la ilustración por debajo de 1024px y, desde 1024px, dos columnas (`grid-template-areas: 'art panel'`, ilustración fija a la izquierda con `AccessPitchComponent` y el formulario a la derecha; en el DOM el formulario va primero). Los campos son de contorno por `MAT_FORM_FIELD_DEFAULT_OPTIONS` en el layout y las esquinas (12px) y alturas de botón (48px) salen de `mat.form-field-overrides` y `mat.button-overrides` dentro de `.access-theme`: ajusta Material por tokens, no por sus clases internas. Roboto se carga en pesos 300 a 500, así que la negrita de la vista usa 500. La presentación de la izquierda es `AccessPitchComponent` o, si la ruta lleva `data: { pitch: 'steps' }` (registro), `AccessStepsComponent`; ambos son tarjetas `.pitch-card` (estilos en `_access-theme.scss`). Los títulos son «Bienvenido de nuevo» y «Crea tu cuenta» con una frase `.lead`; los estados de cuenta (correo enviado, verificando, enlace no válido) van en un panel `.state` con `.state-icon`. Karma mide 800px: el diseño ancho no se prueba allí (sus pruebas se omiten con `pending`), se verifica en Chrome real. `mat-sidenav-content` del shell lleva `box-sizing: border-box` (con `content-box` recortaba el final de cada pantalla en el doble del relleno). El logo original (PNG, solo referencia) sigue en el historial: `c917528^:app/img/`.
- Shell (área privada): desde 960px, riel de iconos (`layout/nav-rail.component.ts`) y barra con título, búsqueda «Buscar o ir a…» (`layout/global-search.component.ts`, Ctrl K, ancla su panel a la píldora con `matAutocompleteOrigin`; el CDK 21 lo adjunta junto al campo, no en el contenedor de overlays), `ThemeToggleComponent` (tres botones, `aria-checked`) y avatar; por debajo, menú desplegable y, bajo 480px, la marca solo con el emblema. Tipografía de marca: Manrope (`typography` de `mat.theme`; `title-medium` queda en Roboto, los nombres de jornada piden `--mat-sys-title-large-font`). Responsive verificado en 320–2560px a ambos lados de 480/720/960/1024/1100; la tarjeta de acceso lleva `min-width: 0` (si no, desborda 14px a 320px). Detalle en `openspec/changes/redesign-access-and-home/`.
- Resto de pantallas (change `redesign-remaining-screens`): botones de 44px con esquinas de 12px y campos con contorno en toda la aplicación (`OUTLINED_FIELDS_PROVIDER` en `app.config.ts`, tokens en `styles.scss`; acceso e Inicio suben a 48px en su hoja); el botón de enviar y la acción de crear de cada pantalla llevan `class="primary-action"` (degradado, una por pantalla). **Todo botón de solo icono lleva `title`**: `ActionTitleDirective` (`shared/ui/`, selector `[mat-icon-button]`, copia el `aria-label`) se importa en cada componente que declare uno; otros controles de icono (`mat-button-toggle`) llevan `[attr.title]`; se comprueba con `iconButtonsWithoutTitle` (`src/testing/`) y el barrido `titulos` del banco visual. Formularios: `FormHeadComponent` (botón de vuelta, un `a mat-stroked-button` de contorno y sin fondo de 44px, sobre el `h1`), secciones `.form-section` con icono o número (`.step-num`), `FormActionsComponent` (proyecta «Cancelar» y «Guardar», avisa de «Cambios sin guardar» y queda fija al pie bajo 720px) y el resumen que acompaña (`.with-summary` + `.summary`: «Así quedará» de configuraciones con `describeSettings`, «Revisa» de planificar). Listados: `DataTableComponent` con filtro de 44px, «Mostrando N de TOTAL» (el filtro solo recorre la página cargada), esqueleto de carga y primera columna fija bajo 720px (`primary` en `DataColumn`), `ListState.countText` en la cabecera y `FleetTabsComponent` entre los tres listados de flota. **Iconos de línea** (change `refine-lists-and-icons`): `mat-icon` pinta con `Material Symbols Outlined` (peso 350, sin relleno; `index.html` y la clase `material-icons` en `styles.scss`) con los mismos nombres que Material Icons, así que no hay que cambiar plantillas; un nombre que la fuente no tenga se vería como texto (la sonda `probe-ligaduras.js` del banco lo detecta). **Listados del diseño**: `DataTableComponent` (estilo en `shared/data/_data-list.scss`, global y colgado de `app-data-table`) con búsqueda de 44px («/» la enfoca), densidad cómoda o compacta (se recuerda en `ruteando-density`), cabecera en monoespaciada, `DataColumn.kind` (`id`, `strong`, `muted`), acciones de fila que aparecen al pasar el cursor, selección (`selectable` + `#selectionActions`, barra pegada al pie), chips de estado con recuento (`facet`) y vista de tarjetas (`#card`, se recuerda en `ruteando-list-view`). Con `FullListState` (paquetes, jornadas, vehículos y lugares: pide las páginas de 100 en 100 hasta 1000) la tabla busca, cuenta y pagina sobre todo; con `ListState` (zonas, configuraciones, tipos y conductores) sigue filtrando solo la página. Cambiar el estado de varios paquetes es una petición por paquete (`package-bulk-status.ts`); lugares lleva `PlacesMapComponent` (un pin por lugar, color y letra por tipo). Mapas: `ThemeService.scheme` (esquema efectivo, sigue al sistema en vivo), `shared/map/map-palette.ts` (OpenLayers dibuja en canvas: los colores se resuelven desde los tokens y se repintan al cambiar el tema), teselas oscurecidas con `className: 'app-tiles'` y un filtro de `shared/map/_map-theme.scss` (que también lleva los controles de OpenLayers a los tokens y el zoom a 44px). Detalle de jornada: una tarjeta por ruta y `.split-view` (mapa fijo desde 1100px). Las pruebas de los mapas fijan el tema claro porque Karma hereda el del sistema operativo. Tablas auxiliares: `table.grid`. **Ninguna tabla se desplaza en horizontal en una pantalla estrecha**: las tablas de datos van en un `.stack-scope` (contenedor de tamaño con nombre `stack`) con `table.stack-table`, y cuando esa caja mide menos de 840px (`@container`, no la ventana) cada fila pasa a ser un bloque (`_ui-system.scss`): la primera celda lleva `primary-cell` (título), las demás `data-label` con su encabezado (`DataTableComponent` lo pone solo; en las tablas propias se escribe a mano junto con los `role`, porque algunos lectores pierden la semántica de una tabla si cambia su `display`), las acciones `actions` y `empty-cell` oculta un dato vacío. Texto solo de tarjeta: `.stack-only`. Medirlo: suite `scroll` del banco (`qa-visual/qa.mjs`). Lo que el gateway no da (filtro y orden en servidor, visitas por jornada) no se simula: ver el change.
- Menú e inicio: `layout/nav-items.ts` define el menú por rol (`navItemsFor`, `areaLinksFor`); lo usan el shell y la página de inicio (`home/`: cabecera con saludo, ilustración de rutas y, para administradores y agentes, las acciones «Planificar jornada» e «Importar paquetes»; accesos a las áreas del rol) y el anillo «Paquetes atendidos» y las cifras de pendientes y sin atender (una sola petición, `GET /packages?page=0&size=100`: el gateway no filtra por estado, así que se cuentan en el cliente los 100 más recientes y la frase dice «los más recientes de N» si hay más; `package-figures.ts`), y las últimas jornadas (con servicios y vehículos solo si el listado los informa; `fetchLatestJourneys`: ordena por `createdAt` en el cliente porque el gateway ignora `sort`, y detecta si el listado viene ascendente; ver `gateway-api.md`).
- Secretos: `GATEWAY_API_KEY` solo vive en el servidor (`.env`, ignorado por git); no la copies a ficheros versionados ni al frontend.
- Historial: el árbol se fusionó desde varias ramas de migración (`codex/migrate-angularjs-app-to-angular`); el proyecto Angular 17.0 anterior y la aplicación AngularJS se eliminaron, y `ng-ruteando` es el único frontend.
